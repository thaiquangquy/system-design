Key-Value Store

A single-node, disk-backed key-value store built from first principles: a write-ahead log, an in-memory memtable, immutable SSTables, and a bloom filter in front of each one — the same primitives real LSM engines like LevelDB, Cassandra, and RocksDB are built on.

Java 21 Spring Boot 3.3 No external deps put(key,value) / get(key) No Docker required for tests
01 — Overview

What this is, and what it deliberately isn't

This service is phase 1 of the design in key-value-store/key-value-storage.md: just the storage engine and its REST API on a single node. The full design also covers running this as an actual distributed store — consistent-hash partitioning, N/W/R quorum replication, vector clocks, gossip failure detection, sloppy quorum, and Merkle-tree anti-entropy — but none of that is built here yet. See Roadmap for the exact line between what exists and what's designed-but-not-built.

The requirement this phase satisfies is small on purpose: two operations, put(key, value) and get(key), over key-value pairs typically under 10KB, with durability across a crash. Everything else in the design doc — automatic scaling, tunable consistency, multi-datacenter replication — is a property of the distributed system this single node is the building block for.

Why no Redis, no Postgres, no Docker in the test suite? The point of this phase is the storage engine itself. Every test, including a full HTTP round-trip test, runs as plain JUnit 5 against the local filesystem — there's nothing external to spin up.
02 — Architecture

Write path and read path

Both paths run through the same three storage tiers — the write-ahead log, the active memtable, and the on-disk SSTables — but touch them in a different order and for a different reason. Toggle between them below.

  1. Append the record to the write-ahead log and fsync it — durable before memory is touched.
  2. Apply the write to the active MemTable (in-memory, sorted, lock-free reads/writes).
  3. When the MemTable's byte size crosses flush-threshold-bytes, swap in a fresh MemTable and write the old one's sorted contents to a new immutable SSTable + bloom filter.
  4. Only after the SSTable is durably registered, rotate (truncate) the WAL — a crash between these two steps just replays a few redundant records on restart, never loses data.
  1. Check the active MemTable first — the freshest data.
  2. If a flush is in-flight, also check the MemTable currently being flushed (closes the race window between swap and disk write).
  3. Check each SSTable, newest-first: the bloom filter usually rules a file out without opening it; otherwise scan with an early exit once a key sorts past the target.
  4. Not found anywhere → 404.

Concurrency note: MemTable is a ConcurrentSkipListMap, safe for concurrent put/get with no external locking. WriteAheadLog.append is synchronized — a deliberate single-writer bottleneck, since interleaved unsynchronized writes could corrupt a frame. StorageEngine's read-write lock guards only the active/flushing memtable pointer swap (a few nanoseconds), so get() never blocks on flush I/O.

03 — File formats

One binary frame, shared by the WAL and every SSTable

Both the write-ahead log and SSTable data files are sequences of the same big-endian, length-prefixed frame. Hover or focus a field for what it's for.

keyLength int32
keyBytes
valueLength int32
valueBytes
crc32 int32

RecordCodec.decode never throws for a torn tail or CRC mismatch — it returns empty, which callers treat as "no more valid records," exactly how a write-ahead log is expected to end after a crash.

  • Write-ahead log (wal.log): a raw, append-ordered sequence of frames. No header, no delete marker — every record is an unconditional put.
  • SSTable (sstable-<20-digit-seq>.data + paired .bloom): frames in ascending key order, for free, since the memtable is already sorted. No sparse index, so a lookup not ruled out by the bloom filter scans sequentially — but stops as soon as a key sorts past the target.
  • Bloom filter (.bloom): bitSizeInBits(int32) | numHashFunctions(int32) | bits. Kirsch-Mitzenmacher double hashing over two independent 64-bit FNV-1a hashes — no external bloom-filter library.
04 — Code tour

Suggested reading order

Seven files, bottom-up: the shared frame codec first, then each storage tier, then the coordinator that ties them together, then the HTTP surface on top.

1 format/RecordCodec.java encode/decode for the shared WAL + SSTable frame ›

Everything else in the engine is built on top of this one frame. Read it first.

public static byte[] encode(String key, String value) {
    byte[] keyBytes = key.getBytes(StandardCharsets.UTF_8);
    byte[] valueBytes = value.getBytes(StandardCharsets.UTF_8);

    ByteBuffer payload = ByteBuffer.allocate(4 + keyBytes.length + 4 + valueBytes.length);
    payload.putInt(keyBytes.length).put(keyBytes).putInt(valueBytes.length).put(valueBytes);
    byte[] payloadBytes = payload.array();

    CRC32 crc = new CRC32();
    crc.update(payloadBytes);

    ByteBuffer frame = ByteBuffer.allocate(payloadBytes.length + 4);
    frame.put(payloadBytes).putInt((int) crc.getValue());
    return frame.array();
}
2 wal/WriteAheadLog.java durable append, crash-safe replay, rotate ›

append is synchronized on purpose — a single-writer bottleneck that trades throughput for the guarantee that a successfully-returned put survives a crash.

public synchronized void append(String key, String value) throws IOException {
    byte[] frame = RecordCodec.encode(key, value);
    file.seek(file.length());
    file.write(frame);
    file.getFD().sync();
}
3 memtable/MemTable.java in-memory sorted store, byte-size accounting for the flush threshold ›

Backed by ConcurrentSkipListMap so concurrent put/get need no external locking, and sortedEntries() yields ascending key order for free — required by the SSTable writer.

private final ConcurrentSkipListMap<String, String> entries = new ConcurrentSkipListMap<>();

public void put(String key, String value) {
    int incomingSize = utf8Length(key) + utf8Length(value);
    String previous = entries.put(key, value);
    if (previous == null) {
        sizeBytes.addAndGet(incomingSize);
    } else {
        int previousSize = utf8Length(key) + utf8Length(previous);
        sizeBytes.addAndGet(incomingSize - previousSize);
    }
}
4 bloom/BloomFilter.java custom bit-array + double-hashing bloom filter, no external lib ›

Kirsch-Mitzenmacher double hashing derives all k bit positions from just two independent hashes (h1 + i·h2) instead of k separate hash functions.

public boolean mightContain(String key) {
    long h1 = hash(key, FNV_OFFSET_BASIS_1);
    long h2 = hash(key, FNV_OFFSET_BASIS_2);
    for (int i = 0; i < numHashFunctions; i++) {
        if (!getBit(bitIndex(h1, h2, i))) {
            return false;
        }
    }
    return true;
}

private int bitIndex(long h1, long h2, int i) {
    long combined = h1 + (long) i * h2;
    return Math.floorMod(combined, bitSizeInBits);
}
5 sstable/SSTableReader.java bloom-check, then sequential scan with early exit ›

Pairs with SSTableWriter (flushes sorted memtable entries to a new file). Entries are sorted, so the scan can stop the moment a key sorts past the target.

public Optional<String> get(String key) throws IOException {
    if (!bloom.mightContain(key)) {
        return Optional.empty();
    }
    try (var in = new DataInputStream(new BufferedInputStream(Files.newInputStream(dataPath)))) {
        while (true) {
            Optional<KvRecord> record = RecordCodec.decode(in);
            if (record.isEmpty()) {
                return Optional.empty();
            }
            int cmp = record.get().key().compareTo(key);
            if (cmp == 0) {
                return Optional.of(record.get().value());
            }
            if (cmp > 0) {
                return Optional.empty();
            }
        }
    }
}
6 engine/StorageEngine.java the coordinator — write/read path, flush-and-swap, recover() ›

The trickiest part of the codebase. flush() swaps in a fresh memtable under a write lock (nanoseconds), writes the old one to disk outside that lock, and only rotates the WAL after the SSTable is durably registered.

private void flush() throws IOException {
    synchronized (flushMonitor) {
        if (!activeMemTable.exceedsThreshold(props.flushThresholdBytes())) {
            return; // another thread already flushed while we waited
        }
        MemTable toFlush;
        swapLock.writeLock().lock();
        try {
            toFlush = activeMemTable;
            flushingMemTable = toFlush;
            activeMemTable = new MemTable();
        } finally {
            swapLock.writeLock().unlock();
        }

        long seq = sstableSequence.getAndIncrement();
        SSTableWriter.write(dataPath(seq), bloomPath(seq), toFlush.sortedEntries(),
                props.bloomExpectedInsertions(), props.bloomFalsePositiveRate());
        sstables.add(0, new SSTableReader(seq, dataPath(seq), bloomPath(seq)));

        // Only rotate the WAL after the SSTable is durably registered: a crash between
        // these two steps just causes a harmless redundant replay on next startup.
        wal.rotate();
        flushingMemTable = null;
    }
}
7 api/KeyValueController.java PUT / GET /api/v1/kv/{key} ›

Thin on purpose — value-size validation, then a direct call into StorageEngine. Exception mapping to 404/413/400 lives in GlobalExceptionHandler.

@PutMapping("/{key}")
public KeyValueResponse put(@PathVariable String key, @Valid @RequestBody PutValueRequest request) throws IOException {
    int valueBytes = request.value().getBytes(StandardCharsets.UTF_8).length;
    if (valueBytes > props.maxValueBytes()) {
        throw new ValueTooLargeException(valueBytes, props.maxValueBytes());
    }
    storageEngine.put(key, request.value());
    return new KeyValueResponse(key, request.value());
}

@GetMapping("/{key}")
public KeyValueResponse get(@PathVariable String key) throws IOException {
    String value = storageEngine.get(key).orElseThrow(() -> new KeyNotFoundException(key));
    return new KeyValueResponse(key, value);
}

06 — Run & test

Getting it running

Build & test

mvn test
mvn test -Dtest=StorageEngineTest
mvn package

Run locally

mvn spring-boot:run

Listens on http://localhost:8080.

curl -X PUT http://localhost:8080/api/v1/kv/hello -H "Content-Type: application/json" -d '{"value": "world"}'
curl http://localhost:8080/api/v1/kv/hello
curl http://localhost:8080/api/v1/kv/does-not-exist
Exercise a flush: put enough distinct keys to cross flush-threshold-bytes, then check data/sstables/ for a new pair of files. Exercise crash recovery: kill the process (no graceful shutdown), restart it against the same data/ directory — every previously-put key, including ones only in the WAL, should still read back.

Docker

docker build -t kv-store .
docker run -p 8080:8080 -v "$(pwd)/data:/app/data" -e KVSTORE_DATA_DIR=/app/data kv-store

Unlike the stateless sibling rate-limiter service, persistence to a mounted host path is the entire point here — skip the volume mount and every write is lost when the container exits.

07 — Roadmap

What's built vs. what's designed

The full distributed design lives in key-value-store/key-value-storage.md. This service only builds the single-node half.

Phase 1 — built

  • Write-ahead log: durable, fsynced append
  • MemTable: in-memory sorted store
  • SSTable + bloom filter: immutable, bloom-guarded lookups
  • Crash recovery: rebuild index, replay WAL, truncate torn tail
  • REST API: PUT/GET with 404 / 413 / 400 mapping
  • Full HTTP round-trip test suite, plain JUnit 5

Future phases — designed, not built

  • Consistent hashing / partitioning across nodes
  • Async replication across N servers
  • Quorum consensus (tunable N/W/R)
  • Vector clocks for conflict resolution
  • Gossip-based failure detection
  • Sloppy quorum + hinted handoff
  • Merkle-tree anti-entropy
  • SSTable compaction & sparse index
  • Delete / tombstone support

The design doc's quorum math, for whenever partitioning lands — with N replicas, a write quorum W, and read quorum R:

W=1 or R=1fast, weaker consistency
W>1 or R>1slower, stronger consistency
R=1, W=Noptimized for fast reads
W=1, R=Noptimized for fast writes
W+R > Nstrong consistency guaranteed — e.g. N=3, W=R=2 → 4>3 ✓
W+R ≤ Nstrong consistency not guaranteed
